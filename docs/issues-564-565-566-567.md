# Issues #564 · #565 · #566 · #567 — Query Performance & Testing Improvements

This document covers four related issues implemented together in a single PR.

---

## #564 — Lazy Loading for Vault Metadata

**Module**: `backend/src/lazy_metadata.rs`  
**Migration**: `17` (adds `vault_metadata` table)

### Problem
The `Vault` struct always loaded all associated data eagerly. Large metadata
blobs (e.g. template overrides, custom fields) inflated every vault query even
when the caller only needed core fields.

### Solution
Metadata is stored in a separate `vault_metadata` table and fetched on demand
via `LazyMetadataLoader`.

```rust
// Write metadata
let loader = LazyMetadataLoader::new(Arc::clone(&db));
loader.set(VaultMetadata {
    vault_id: "vault-123".to_string(),
    fields: serde_json::json!({"note": "estate plan"}),
    updated_at: Utc::now(),
})?;

// Read metadata (cache-backed, falls through to SQLite on miss)
let meta = loader.get("vault-123");
```

### Cache behaviour
- Default TTL: **5 minutes**; configurable via `MetadataCacheConfig`.
- Maximum entries: **1 000**; LRU eviction when exceeded.
- Writes (`set`) and deletes (`delete`) always invalidate the cache entry.

## #565 — View-Based Query Optimization (Materialized Views)

**Module**: `backend/src/materialized_views.rs`  
**Migration**: `18` (adds `vault_summary_view` and `vault_owner_counts_view`)

### Problem
Dashboard and analytics endpoints recomputed vault aggregates (total count,
active count, released count, average interval) on every request with a full
table scan.

### Solution
Precomputed aggregates are stored in `vault_summary_view` (singleton row) and
`vault_owner_counts_view` (per-owner row).

```rust
let mgr = MaterializedViewManager::new(Arc::clone(&db));

// Full refresh on startup / periodically
mgr.refresh_all()?;

// Fast read — no table scan
let summary = mgr.get_vault_summary().unwrap();
println!("{} active, {} released", summary.active_vaults, summary.released_vaults);

// Incremental update on vault status change (cheaper than full refresh)
mgr.apply_incremental_vault_update(Some("active"), Some("released"))?;
```

### Refresh schedule
- Default interval: **5 minutes** (background scheduler).
- `refresh_due_views()` should be called from the scheduler job loop.
- `is_due("vault_summary_view")` checks whether a refresh is overdue.

## #566 — Query Plan Optimization

**Module**: `backend/src/query_optimizer.rs`  
**Migration**: `19` (adds composite and single-column indexes on `vaults`)

### Problem
`search_vaults` built filter predicates in declaration order, which could
prevent the query planner from using composite indexes.

### Solution
`QueryPlanner` selects the optimal `PlanStrategy` based on filter presence and
emits SQL with predicates ordered by selectivity (owner first, then status,
then date ranges).

```rust
let runner = OptimizedQueryRunner::new(Arc::clone(&db));
let plan = runner.get_plan(&query);
// plan.strategy is e.g. PlanStrategy::OwnerStatusIndex

// Diagnostic: print the SQLite query plan
for row in runner.explain_plan(&query) {
    println!("{row}");
}
```

### Indexes added (migration 19)
| Index | Columns | Benefits |
|---|---|---|
| `idx_vaults_owner` | `owner` | owner-only queries |
| `idx_vaults_status` | `status` | status-only queries |
| `idx_vaults_owner_status` | `owner, status` | most common combined filter |
| `idx_vaults_created_at` | `created_at` | date-range queries |
| `idx_vaults_owner_created_at` | `owner, created_at` | owner + date |

### Plan cache
Plans are cached for **10 minutes** keyed on a shape fingerprint (presence of
filters, not their values) so repeated calls with different values but the same
predicates share one cached plan.

## #567 — Property-Based Testing

**Module**: `backend/src/property_tests.rs`  
**Framework**: `proptest` (added to `[dev-dependencies]`)

### Problem
Unit tests only verified specific hand-picked inputs. Edge cases in arithmetic,
state machines, and pagination were difficult to discover manually.

### Properties tested
| Property | Generator | Invariant |
|---|---|---|
| Balance invariant | random deposit/withdraw sequences | `balance ∈ [0, initial + deposits]` |
| TTL monotonicity | random intervals | `ttl` never decreases on check-in |
| Status machine | random op sequences | once Released, always Released |
| No double release | random op sequences | release count ≤ 1 |
| `QueryCache` round-trip | random vault IDs + values | inserted value is retrievable |
| Query plan fingerprint | same shape, different values | fingerprints are equal |
| Plan determinism | random filter presence | same query → same SQL/strategy |
| Materialized view counters | random vault counts | full refresh matches `COUNT(*)` |
| `LazyMetadataLoader` round-trip | random vault IDs + fields | set then get returns same fields |
| Metadata delete | random vault IDs | deleted metadata returns `None` |
| Pagination completeness | random vault count + page size | all pages union = total |

### Fuzz-derived regression tests
The following edge cases were identified via fuzz input analysis and encoded as
named regression tests:

- `regression_zero_check_in_interval` — zero interval clamps to `VAULT_TTL_LEDGERS_MIN`
- `regression_max_check_in_interval_no_overflow` — `u64::MAX` interval clamps to `MAX_PERSISTENT_TTL`
- `regression_i128_min_balance_guarded_withdrawal` — guarded withdraw never underflows
- `regression_query_cache_default_ttl_used_when_override_is_none` — default TTL path
- `regression_query_cache_empty_vault_id_key` — empty string key is valid
- `regression_lazy_loader_empty_vault_id` — empty vault ID returns `None` cleanly
- `regression_materialized_view_zero_vaults` — zero-vault DB produces all-zero summary

### Running
```bash
# Run all property tests (same as regular tests)
cargo test -p ethos-protocol-backend property_tests

# Increase proptest cases (set in environment)
PROPTEST_CASES=10000 cargo test -p ethos-protocol-backend property_tests
```
